# Проектные решения

Краткие записи о принятых решениях. Формат: контекст — решение —
причины — альтернативы — следствия.

## Решение 1. Формат входных файлов — JSON

**Контекст.** `lab1.md` требует «путь к файлу», не уточняя формат.
Для МТ и НАМ формат не задан.

**Решение.** JSON для обеих машин.

**Причины.**
- Единый парсер для МТ и НАМ.
- Явное поле для начального слова.
- Стандартный `json.loads` из stdlib.
- Понятная обработка ошибок (`JSONDecodeError`).

**Альтернативы.** Plain text для НАМ (ближе к духу переписывания строк,
но требует двух парсеров и негде хранить начальное слово);
свой формат (надо писать парсер с нуля).

**Следствия.** `MarkovAlgorithm._parse` использует `json.loads`.
При необходимости поддержать plain text — добавить метод
`from_rules_text`, не ломая текущий.

## Решение 2. Строка правила — пять полей через пробел

**Контекст.** Формат правила МТ нужно зафиксировать.

**Решение.** `"q0 1 q1 0 R"` — текущее состояние, читаемый символ,
следующее состояние, записываемый символ, направление.

**Причины.**
- Совпадает с классическим описанием МТ.
- Легко парсится и печатается.
- Читается глазами.

**Альтернативы.** JSON-объект на каждое правило (избыточно);
`q0,1->q1,0,R` (сложнее парсить, путаются запятые и стрелки).

**Следствия.** `Transition._parse` разбивает строку по пробелам.

## Решение 3. Каретка вынесена в отдельный класс `Head`

**Контекст.** Задание 1.8 упоминает «каретку» как отдельную сущность.

**Решение.** `Head` — отдельный класс, не поле `Tape`.

**Причины.**
- Соответствует формулировке задания.
- Позволяет менять представление ленты, не трогая каретку.
- Соответствует принципу единственной ответственности.

**Альтернативы.** Хранить позицию в `Tape` (смешивает две
ответственности).

**Следствия.** `TuringMachine` хранит `_tape` и `_head` отдельно.

## Решение 4. Направление — `Enum` с тремя значениями

**Контекст.** В описаниях МТ обычно только L и R.

**Решение.** `Direction` содержит `LEFT`, `RIGHT` и `STAY`.

**Причины.**
- `STAY` допустим в ряде формулировок МТ.
- Позволяет описывать правила, не двигающие каретку (например,
  `q0 _ q_accept _ S`).
- Не усложняет код: `Head.move` просто ничего не делает для `STAY`.

**Альтернативы.** Только L/R (пришлось бы кодировать остановку иначе).

**Следствия.** В правилах допустим символ `S`.

## Решение 5. Управление шагами — `run(on_step=...)`

**Контекст.** Флаг `-log` требует печатать состояние после каждого
шага. UI не должен знать о внутреннем цикле `run`.

**Решение.** `run` принимает опциональный callback `on_step`.

**Причины.**
- UI передаёт функцию логирования, не дублируя цикл.
- Домен не знает о печати — остаётся чистым.
- Тесты используют hook для проверки числа шагов.

**Альтернативы.** Печатать прямо в `run` (домен зависит от UI);
дублировать цикл в меню (нарушение DRY).

**Следствия.** Сигнатура `run(max_steps, on_step)`.
